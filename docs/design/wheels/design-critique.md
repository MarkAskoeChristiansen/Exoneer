# Adversarial review – wheel pass design documents

## A. Engine and API errors

**A1. The entire physics integration strategy rests on an API behavior that UE 5.8 does not have. (Doc 1 sections 6.1/6.2, Doc 2 sections 3-4, and the agent2 premise both docs inherited.)**
Claim: `FBodyInstance::AddCustomPhysics` registers a delegate that Chaos invokes per substep on the physics thread.
Reality, verified in engine source: under Chaos, `FPhysScene_Chaos::AddCustomPhysics_AssumesLocked` is `CalculateCustomPhysics.ExecuteIfBound(MDeltaTime, BodyInstance);` – the delegate executes **immediately, once, synchronously on the calling (game) thread**, with `MDeltaTime = min(frame dt, MaxSubsteps * MaxSubstepDeltaTime)` (ChaosScene.cpp:340). There is no registration, no list "consumed each physics step" (Doc 2), no per-substep re-evaluation, no physics-thread execution. That was PhysX-era behavior; PhysSubstepTasks is legacy. Chaos does consume `bSubstepping`/`MaxSubstepDeltaTime`/`MaxSubsteps` (solver-internal steps via `SetMaxDeltaTime_External`/`SetMaxSubSteps_External`), but a force computed once per frame is held constant across those internal steps. Consequences: Doc 1's suspension/slip stability analysis (6.3) is computed at the wrong dt (it assumes 1/60 substeps; the real evaluation dt is frame dt, up to the 0.05 s clamp, where its own bound `k_s <= 0.25*m/dt^2` fails: at dt = 0.05, bound = 25 000 < the chosen 40 000), the slip integration is frame-rate dependent (the exact failure agent2 predicted), and Doc 2's "no locks needed" threading note is argued from a false premise.
Fix: use the Chaos sim-callback mechanism – `Solver->CreateAndRegisterSimCallbackObject_External<T>()` with `OnPreSimulate_Internal()` running per internal solver step with `GetDeltaTime_Internal()`; this is exactly how the already-enabled ChaosVehicles plugin does it (ChaosVehicleManager.cpp:82). One construct-owned callback for all wheels (also needed for Dynamic Dampening's cross-wheel `W_avg`), per-frame contact cache marshaled as callback input, forces applied through the internal particle handle, outputs marshaled back. New work this creates that no document lists: add `"Chaos"` to `Exoneer.Build.cs`; unregister/free the callback on construct `EndPlay`/destruction and clear a wheel's input slot in `Shutdown()`. Fallback if the callback proves too heavy for this pass: accept once-per-frame evaluation, recompute every stability bound at worst-case frame dt, and say so – do not ship the current text claiming substep fidelity it does not have.

**A2. Doc 2's call `GetBodyInstance()->AddCustomPhysics(FCalculateCustomPhysics::CreateUObject(...))` does not compile.** `AddCustomPhysics` takes `FCalculateCustomPhysics&` (non-const lvalue reference, BodyInstance.cpp:3726); a temporary from `CreateUObject` cannot bind to it. The old pattern required a stored member delegate. Moot after A1, but it shows the pattern was never compiled.

**A3. Doc 3's collision config section name is wrong.** `[/Script/Engine.CollisionProfiles]` (plural) is not read; the class is `UCollisionProfile`, `config=Engine`, so the section is `[/Script/Engine.CollisionProfile]` (Doc 2 has it right). With the wrong section the WheelProbe channel is silently never registered – the same class of dead-config bug as the `PhysicSubstepDeltaTime` key this pass exists to fix. Use Doc 2's block verbatim.

**A4. Doc 3's automation test flags do not compile in 5.8.** `EAutomationTestFlags::ApplicationContextMask` does not exist; since the enum-class conversion it is the global constant `EAutomationTestFlags_ApplicationContextMask` (AutomationTest.h:144). Doc 2's `EAutomationTestFlags::EditorContext | EAutomationTestFlags::ProductFilter` is valid. Unify on Doc 2's flags.

**A5. Doc 3's ground material instances will silently resolve to no physical material.** Setting `phys_material` on the MIC is not enough: `UMaterialInstance::GetPhysicalMaterial()` returns the instance's `PhysMaterial` only when `bOverridePhysMaterial` is true (MaterialInstance.cpp:2157; the property defaults to false). The bootstrap must also `set_editor_property("override_phys_material", True)`, or every wheel hit on the sand/clay fields falls through to the firm-ground fallback and the whole soft-soil test range is inert.

**A6. Doc 3's HUD accessor signature is illegal.** `const FVehicleDrivetrainSummary& GetDrivetrainSummary() const` as a `BlueprintPure` UFUNCTION – UHT rejects const-reference struct returns. Doc 2's by-value version is correct; also the two structs disagree (4 fields vs 7). Adopt Doc 2's struct and signature.

**A7. Minor: Doc 3 instructs C++ to "set the ghost-box response to ECR_Ignore on this channel".** Unnecessary – ghost boxes already do `SetCollisionResponseToAllChannels(ECR_Ignore)` then block only Visibility (verified VehicleConstruct.cpp:1344-1348), so they ignore any new channel by construction. Harmless, but delete it so nobody adds dead code.

## B. Physics and math errors

**B1. Doc 1 section 7.3 (Dynamic Dampening) has a sign error that makes the controller diverge.** With `C = clamp(L0 - u_i - d_free, ...)` (section 3 step 3), raising `u_i` lowers compression and therefore lowers `W_i`. So an overloaded wheel needs `du_i/dt > 0`. The stated law `du_i/dt = -k_bal (W_i - W_avg)` is positive feedback: it lowers `u_i` on the loaded wheel, raising its load further until the `±0.5 x_t` clamp rails – maximizing imbalance instead of minimizing it. Fix: `du_i/dt = +k_bal (W_i - W_avg)`; with `k_bal = 1/(tau k_s)` this gives clean exponential convergence to the mean with time constant tau.

**B2. Doc 2 implements only the flexible-tire branch; Doc 3's predictions are built on it; Doc 1's own regime criterion contradicts both.** Doc 2 step 4 always sets `p = p_i + p_c`; Doc 1 section 4.1 correctly requires Wong's `p_gcr` criterion with a rigid implicit solve above it. Check with Doc 3's authored numbers (W ≈ 2.06 kN, b = 0.25, D = 0.7 m, LLL dry sand): `p_gcr ≈ 65 kPa`. At the authored nominal 220 kPa the tire is deep in the **rigid** regime, where the implicit solve gives z ≈ 4.3 cm and R ≈ 0.26 kN per wheel – the rover does not bog at road pressure, and CTIS from 220 to 90 kPa changes nothing because the flexible regime only engages below `p_i ≈ 30 kPa` (with a 35 kPa carcass), which is under the 60 kPa debead floor. Doc 3's headline behaviors (17 cm sinkage at 220 kPa, bogging, CTIS rescue at ~90 kPa) exist only in the flexible-always simplification Doc 1 rejects – and Doc 1 is right physically (an over-inflated tire's ground pressure is not its inflation pressure). Fix: implement Doc 1's dual regime as specified, then retune the wheel/soil parameter set so the CTIS band actually straddles `p_gcr` at rover loads (levers: lower carcass pressure, narrower band soils, wheel width, load), and re-derive every predicted number, HUD threshold, and checklist expectation from the merged model. This retuning is a real work item; without it Mark's first soft-soil session tests a story the physics will not tell.

**B3. Doc 2 omits slip sinkage and bulldozing, which deletes the scope's core mechanic.** In pure Janosi form, gross F is **monotonically increasing** in s and R is slip-independent, so full throttle is always optimal and "raw throttle drives s toward 1.0 and you dig in" (GAME-SCOPE 4.1) can never happen. Doc 1's `n_eff = n0 + n1|s|` plus `R_b` is what creates it. Doc 2's soil class is missing the `n1` and `gamma_s` fields, and Doc 3's soil contract is missing `n1`, `gamma_s`, and `K_y`. Fix: canonical `FSoilParams = {k_c, k_phi, n0, n1, c, phi, K, K_y, gamma_s}` in the physmat, the bootstrap contract, and the math library.

**B4. Doc 3's required monotonicity test is mathematically wrong and would fail a correct implementation.** "F falling as s goes 0.25 to 1.0": with l = 0.1, K = 0.025, the slip bracket is 0.368 at s = 0.25 and 0.755 at s = 1.0 – F rises and saturates. What falls with slip is drawbar pull once slip sinkage raises R. Replace the assert with: F monotone rising, bounded by `A·c + W·tan(phi)`; and DP(s) with `n_eff` peaking inside roughly 0.15-0.25.

**B5. Doc 3's traction margins misuse the shear budget as available thrust; by its own numbers, checklist steps 3, 5, and 6 fail.** "4.5 kN available" is the s→∞ asymptote of `A·c + W·tan(phi)`. Inside the claimed optimal window (s = 0.15-0.25, l ≈ 0.10 m, K = 0.025) the developed force is ~31 percent of budget ≈ 1.4 kN – below the 2.6 kN flat-sand resistance at 80 kPa ("drives with margin" is false; it barely creeps at s ≈ 0.5) and far below the ~4.0 kN needed on the 10 degree ramp (max F(s=1) ≈ 3.4 kN, so the ramp is unclimbable at any slip; "it should just climb" is false). Spot-checks that do pass as pure arithmetic: sinkage 0.0682 m (sand) and 0.0115 m (clay) at 80 kPa/b = 0.25, R = 649 N, slip term 0.3116, F = 349 N, clay budget 2.3 kN, grade forces 1.43/2.84 kN. The formulas were transcribed correctly; the gameplay conclusions drawn from them were not. Fix: re-derive all playtest expectations from the merged (dual-regime, slip-sinkage) model, and retune ramp angles/soil/geometry until the intended lessons genuinely occur in the target slip window.

**B6. No document can hold a braked rover on a slope – checklist step 7 fails by construction.** With slip regularized by `v_eps`, shear force vanishes at zero relative velocity, so a locked-brake rover on the 10 degree ramp settles into steady creep (order 2 cm/s with Doc 3's numbers – visibly failing "must hold, not creep"). Missing work item in all three docs: a stiction branch – when brakes are locked and contact-point speed is below a threshold, apply a velocity-cancelling holding force at the contact, capped by both the shear budget and brake torque over radius. Physical static friction, not a constraint hack.

**B7. Doc 1 arithmetic spot-checks.** T1, T2, T3, T4, T5, T6, T7, T9, T10, T11 and the T8 regime/sinkage/CTIS numbers all recompute correctly to stated precision (verified by hand, including the Newton iterates and the 52 percent resistance-growth claim). Two slips: T8's `R_c = 208.2 N` recomputes to 209.1 N (0.4 percent, outside its own 1e-3 tolerance – recompute before baking into asserts), and the 4.2 chord-vs-arc prose says the arc overestimates by "15 percent at z = 0.2 r_w" where the true figure is ~7 percent (acos(0.8) = 0.6435 vs chord 0.6). Cosmetic; the chord choice itself is sound.

**B8. The power models contradict each other, and Doc 2's version cancels the intended survival pressure.** Doc 2's `GetCurrentDraw = P_mech/eta + 0.1*throttle*|PowerDelta|`, capped at `|PowerDelta|`, has no stall (copper) loss: a motor stalled in mud draws ~watts, so "stalling drains batteries" never happens. Worse, Doc 3 authors `power=-50` as *idle* draw while Doc 2 defines `PowerDelta` as *rated wattage* and caps at it – merged as written, four motors can never draw more than 200 W total and batteries effectively never drain. Doc 3's own "10 kW soft-soil draw" is unreachable from 4 × (180 N·m, 25 rad/s, η 0.85) ≈ 5.3 kW without copper loss. Also note the existing ledger only auto-adds idle `PowerDelta` for module-less blocks, so the wheel module must report idle itself. Fix: adopt Doc 1 section 5.5 verbatim (`P_elec = max(T·ω,0)/η + P_cu0·(T/T_s)²`), add `P_cu0` to the wheel spec, set `PowerDelta` to the rated electrical wattage (≈ −2500), fold idle into `GetCurrentDraw`, and delete the 0.1 magic factor (it is exactly the kind of abstract coefficient the scope bans).
